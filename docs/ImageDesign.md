### Product Images

Photos for a product. Each product can have several images, shown as a gallery, and the first one in display order is the product's main photo -- the one shown in product lists and on the POS grid. Images belong to the product rather than to individual variants, because most photos are shared: a 5 oz and a 16 oz bag of treats look the same. When a variant does need its own photo (a red collar vs. a blue one), the variant points to one of its product's images through `ProductVariant.ImageId`, so one photo can serve several variants (Red / S, Red / M and Red / L all use the red photo).

The image files themselves live in S3 and are served publicly through CloudFront; this table only stores each file's S3 key. Product photos aren't secret, so the API returns plain CloudFront URLs and the frontend uses them directly in `<img>` tags -- no signing is needed to display them.

**How uploading works:**
1. The client calls `POST /products/{productId}/images/upload-url` with the file type and size. The API checks the upload rules below, picks a new key under a `pending/` prefix, and returns a presigned S3 upload URL that expires after about 10 minutes.
2. The client uploads the file directly to S3 with that URL. The file never passes through the API.
3. The client calls `POST /products/{productId}/images` with the key. The API checks the file exists in S3, moves it from `pending/` to its final key, and saves the image row.

Uploads that are never attached are cleaned up by an S3 lifecycle rule that deletes anything under `pending/` after one day.

**Upload rules:** JPEG, PNG or WebP only; at most 5 MB per file; at most 10 images per product.


| Column | Type | Nullable | Unique | Default | Description | Notes |
| ----- | ----- | ----- | ----- | ----- | ----- | ----- |
| `Id` | uuid | No | Yes (PK) | `gen_random_uuid()` | Primary key for the image. | Generated by Postgres. |
| `ProductId` | uuid | No | No | — | The product this image belongs to. | FK to `Products`. Also `UNIQUE (ProductId, Id)` so variants can check the image belongs to their product. |
| `ImageKey` | text | No | Yes | — | The S3 key of the file. | The API builds the full CloudFront URL from this. |
| `AltText` | text | Yes | No | — | Short description of the photo, e.g. "Red nylon collar, side view." | Used by screen readers and shown if the image fails to load. |
| `SortOrder` | int | No | No | `0` | Display order in the product's gallery. | The first image is the product's main photo. |
| `CreatedAt` | timestamptz | No | No | `now()` | When the image was added. | Database-owned. |
| `UpdatedAt` | timestamptz | No | No | `now()` | When alt text or order last changed. | Database-owned; advanced by trigger. |
| `CreatedBy` | uuid | No | No | — | Who created the image. | Set by the app on insert, from the JWT `sub`. |
| `UpdatedBy` | uuid | No | No | — | Who last changed the image. | Set by the app on every insert and update. |


- **Id** -- Primary key, generated by Postgres (`gen_random_uuid()`) when the row is inserted. Variants refer to an image by this id.
- **ProductId** -- The product the image belongs to. An image never moves to another product. The extra `UNIQUE (ProductId, Id)` lets `ProductVariant` use a two-column foreign key, so a variant can only point to an image from its own product.
- **ImageKey** -- Where the file lives in S3, e.g. `products/7f3a9c2e-1b4d-4e8a-9c6f-2d5e8a1b0c3d/a1b2c3d4.jpg`. Only the key is stored, never a full URL, so the CDN domain or bucket can change in config without updating rows. Every upload gets a new key, so browsers and CloudFront never keep showing an old photo from cache.
- **AltText** -- A short description of what the photo shows. Optional, but recommended: screen readers read it aloud, and browsers show it if the image fails to load.
- **SortOrder** -- The image's position in the gallery, lowest first; ties are broken by `CreatedAt`. The first image is the product's main photo, so "set as main photo" is just moving an image to the front with the reorder endpoint. New images are added to the end.
- **CreatedAt / UpdatedAt** -- Same database-owned pattern as every other table (see [Vendor](VendorDesign.md)). There's no `ArchivedAt`: nothing historical references a photo, so removing one is a real delete. The row is deleted first and the S3 file second, so a failed S3 delete only leaves a harmless leftover file instead of a broken image. Variants that pointed to a deleted image have their `ImageId` cleared and fall back to the product's main photo.

### Product Images REST APIs
| Method | Endpoint | Description |
| ----- | ----- | ----- |
| `POST`  | `/products/{productId}/images/upload-url`  | Get a presigned S3 URL to upload a photo (send file type and size; returns `uploadUrl` and `key`) |
| `POST`  | `/products/{productId}/images`  | Attach an uploaded photo (`key`, `altText`); added to the end of the gallery |
| `GET`  | `/products/{productId}/images`  | List a product's images in display order |
| `PATCH`  | `/products/{productId}/images/{imageId}`  | Update an image's alt text |
| `PUT`  | `/products/{productId}/images/order`  | Reorder the gallery with `{ "imageIds": [...] }`; the first image becomes the main photo |
| `DELETE`  | `/products/{productId}/images/{imageId}`  | Remove an image and delete its S3 file; variants using it fall back to the main photo |
